# Linear decomposition

Use this only when confirmed, clear work exceeds one fresh agent context window.

## Model

The parent indexes one outcome and its scope. Each child owns a narrow,
complete, independently demonstrable or verifiable behavior.

Parent-child means the slice belongs to the outcome. Blocking means the slice
cannot start until another completes. Represent both facts with native Linear
relationships when available.

Keep one issue for one coherent outcome. Use vertical slices rather than
technical layers. For a broad mechanical migration, use expand-contract:
additive expansion, independently safe migration batches, then the final
contract step.

Do not decompose unverified reports, unresolved decisions, or autonomous
agent-discovered captures.

## Propose

Present a numbered breakdown with each child's title, blockers, delivered
behavior, and acceptance criteria. Ask the user to approve or revise the
granularity and blocker edges. Create no comments, readiness changes, children,
or relationships before that approval.

## Publish

1. Search for duplicates across the overall outcome and every child.
2. Retain an existing investigated issue as the parent. For direct capture,
   create a concise umbrella parent only after approval.
3. Rewrite the parent body as a current index of the outcome, scope, children,
   and sequencing. Remove implementation detail now owned by children.
4. Create every child as a native child with a complete canonical body and its
   actual readiness.
5. Wire blocking edges after every child has an identifier.
6. Keep the parent in `Backlog` with no readiness label and unset priority.
7. Add one concise parent activity comment recording the approved decomposition
   and body update.
8. Re-read the parent and every child. Verify bodies, status, labels,
   parent-child relationships, and blocker edges.

Return every identifier and link, child readiness and blockers, and any partial
result.
